# Delhivery Last-Mile Delay Intelligence Pipeline

Capstone project, Artificial Intelligence and Machine Learning Certification Program, E&ICT Academy, IIT Roorkee.

Everything runs offline on free libraries (pandas, NumPy, scikit-learn, joblib). The data is synthetic, produced by `generate_data.py`; Delhivery's real records are not used. Money is in Indian Rupees (INR).

The repository answers three questions in one connected pipeline: how long will a parcel take (Part B), which parcels will miss their promise (Part C), and which hubs need which playbook (Part D). Part A prepares the data for all of them. The cleaning and feature functions live once in `src/shipment_prep.py` and are reused by Part A and by the scoring script, so training and prediction apply exactly the same preprocessing.

## How to run

From a fresh clone of the `main` branch (Python 3.11 or newer):

```
pip install -r requirements.txt
python generate_data.py          # prints: 24 1224 48
python part_a_clean_eda.py
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py
python package_model.py
python predict_delay.py
```

The scripts must be run in this order because each one reads files written by an earlier one. `models/delay_model.pkl` is regenerated by running `python package_model.py`. The committed pickle loads reliably only on the scikit-learn version pinned in `requirements.txt` (scikit-learn 1.9.0); if your installed versions differ, re-run `package_model.py` instead of loading the committed pickle. Every random step uses `random_state=42` (the data generator uses its own fixed seeds), so repeated runs give the same files; running `predict_delay.py` twice gives byte-identical output.

`requirements.txt` pins the four packages to the exact versions used:

```
pandas==3.0.1
numpy==2.4.3
scikit-learn==1.9.0
joblib==1.5.3
```

## Data findings

The raw export had 1,224 rows. After removing 24 exact duplicates, 1,200 shipments remain, of which 278 are delayed (delay rate 0.2317). These figures are in `outputs/part_a_checks.csv`; the tables below are in `outputs/part_a_delay_by_group.csv` and `outputs/part_a_correlations.csv`.

- **Service type.** Express parcels are delayed most often: 119 of 243, a delay rate of 0.4897. Standard is 0.2056 and Economy only 0.0857. Express has the tightest promise (36 hours), so even small slippage turns into a miss.
- **Hub tier.** The delay rate climbs steeply with tier: 0.0400 for Tier 1, 0.2150 for Tier 2 and 0.4400 for Tier 3.
- **Distance.** The delay rate rises sharply with distance: 0.0219 for 0-200 km, 0.1368 for 201-400 km, 0.4364 for 401-600 km and 0.8523 for 601+ km. Mean delivery hours rise from 46.7559 to 72.2608 over the same bands.
- **Strongest correlations with `delivery_hours`** (ranked by absolute value, excluding `delivery_hours` itself): `promised_hours` +0.8372, `distance_km` +0.4013 and `n_stops` +0.3247. Next are `hub_daily_capacity` at -0.3237 and `hub_tier` at +0.3175. Longer promises, longer lanes and more stops all mean more hours; bigger-capacity hubs are faster.
- **Why `declared_value_inr` was log-transformed.** On the median-filled column the mean is INR 1,533.0542 but the median is INR 1,121.5, so a few very expensive parcels pull the mean up (right skew); after the natural log the mean (7.0277) and the median (7.0224) almost coincide, giving a symmetric feature.

Data cleaning in numbers (from `part_a_checks.csv`): 36 missing distances, 24 missing weights plus 5 sentinel weights (999 kg, treated as missing), 12 missing declared values and 18 missing payment modes were filled or labelled; 12 messy service-type spellings collapsed to 3. After the hub merge there are still 1,200 rows and 0 missing cells across the 17 features, `delivery_hours` and `is_delayed`. Delivery hours quartiles are 43.255 (Q1) and 72.5625 (Q3); the 1.5 x IQR rule gives bounds of -0.7063 and 116.5238, flagging 1 outlier.

## Model results (regression)

Split: 840 training, 180 validation, 180 test rows. The scaler was fitted on training rows only: the scaled training columns have a largest absolute mean of about 4e-16 (shown as 0.0 after rounding to 4 places), while the scaled test rows give 0.2187 (`part_b_checks.csv`), which proves the scaler did not see the test rows.

- **Baseline.** Predicting the training mean for every validation parcel gives R2 of -0.0212 (RMSE 18.8552 hours). An R2 of about zero means it explains none of the variation in delivery time; every real model beats it by a wide margin.
- **Winner on validation.** Linear regression won with a validation RMSE of 4.8912 hours (R2 0.9313), marginally ahead of gradient boosting at 4.9165 hours (R2 0.9306). Random forest (R2 0.9141) and the depth-6 decision tree (R2 0.8867) were further back.
- **Tree depth (`part_b_tree_depth.csv`).** Depth 1 is high-bias: train and validation RMSE are both high (12.1324 validation vs 11.6334 training, gap 0.499). The unlimited tree is high-variance: train RMSE falls to 0.0000 while validation RMSE is 7.7890, a gap of 7.789. The best depth is 6 (validation RMSE 6.2796), where the tree has captured most signal without yet memorising noise.
- **Learning rate (`part_b_gb_learning_rate.csv`).** 0.1 is best (validation R2 0.9306). 0.01 is too slow: the model under-fits in 100 trees (R2 0.7127). 1.0 overshoots: the large step size makes each tree over-correct and degrades the ensemble (R2 0.8440).
- **Cross-validation (`part_b_cv.csv`).** The two best models by validation RMSE (linear regression and gradient boosting) were re-scored with 5-fold CV on the 1,020 training-plus-validation rows. Linear regression has mean R2 0.9261 (std 0.0048) and gradient boosting 0.9352 (std 0.0044). The CV ranking (gradient boosting higher) disagrees slightly with the validation ranking (linear regression lower RMSE). I would ship linear regression: it has the lowest validation RMSE, the difference between the two is well inside the CV spread, and a linear model is simpler to explain to planners.
- **Final model.** Linear regression, scored once on the held-out test rows, gives R2 0.9493 (RMSE 4.5235 hours).

## Model results (classification)

Stratified split: 840 training, 180 validation, 180 test rows, with 195 / 42 / 41 delayed parcels.

- **Blind baseline.** Predicting "not delayed" for every parcel gives validation accuracy 0.7667 (`part_c_models.csv`), but that is just the non-delayed share. It catches zero delayed parcels (precision 0, recall 0, F1 0), so it is useless for the ops goal of proactive calls.
- **Signal vs noise (`part_c_feature_scores.csv`).** The five bookkeeping noise columns together hold 0.2245 of the random forest's importance, but all five fall outside the top 7 by F-score (F-scores below 10, while the weakest of the top 7 has an F-score of 36.7281). The seven signal columns are `distance_km`, `hub_tier`, `hub_daily_capacity`, `n_stops`, `promised_hours`, `rain_flag` and `sale_event_flag`.
- **SelectK (`part_c_selectk.csv`).** F1 peaks at k=7 (0.8333); k=5 drops to 0.6988, and adding the weak columns back (k=10, 12, 17) brings in noise that lowers F1 to 0.7848-0.8049. Seven columns is the sweet spot.
- **Tuning (`part_c_tuning.csv`).** The untuned default forest on the 7 selected columns scored validation F1 0.8333, higher than the grid search (0.7750) and the randomized search (0.7848). Tuning the forest on a 180-row validation set over-fits the validation fold and does not beat the simpler default; I therefore ship the untuned configuration (chosen_from = default_forest_same_7_features).
- **Alert threshold (`part_c_thresholds.csv`).** By the operations rule (highest threshold with validation recall at least 0.80), the chosen threshold is 0.5. At 0.5 the validation precision is 0.7955, recall 0.8333 and F1 0.814; raising the threshold lifts precision but drops recall below 0.80 (0.7619 at 0.6), so 0.5 keeps enough recall to be useful while keeping false calls low.
- **Test (`part_c_final_test.csv`).** On the held-out test rows at threshold 0.5: precision 0.6889, recall 0.7561, F1 0.7209. Test recall (0.7561) is below validation recall (0.8333); this is honest variation on a small test set with only 41 delayed parcels, not a sign of a broken threshold.

## Operations recommendation

**Escalate hubs.** The Escalate segment has 9 hubs with a mean delay rate of 0.4600 (`segment_profile.csv`): HUB13 Nagpur (0.46), HUB15 Kochi (0.36), HUB17 Patna (0.46), HUB18 Ranchi (0.38), HUB19 Guwahati (0.62), HUB20 Raipur (0.48), HUB21 Bhubaneswar (0.40), HUB23 Siliguri (0.44) and HUB24 Agartala (0.54). These are the stretched hubs where the escalation playbook (extra riders, hub-manager oversight) belongs. HUB19 Guwahati (0.62) and HUB24 Agartala (0.54) are the worst.

**Tier labels that mislead (`tier_vs_segment_mismatch.csv`).** Four hubs behave unlike their tier label:
- HUB07 Kolkata is labelled Tier 1 but operates like a Watch hub - its Tier 1 "metro" label overstates its reliability.
- HUB13 Nagpur is labelled Tier 2 but operates like an Escalate hub - it should be managed with the stretched playbook, not the regional one.
- HUB15 Kochi is also labelled Tier 2 but lands in Escalate for the same reason.
- HUB22 Dehradun is labelled Tier 3 but operates like a Watch hub - it is healthier than its tier suggests, so it need not carry the full escalation overhead.
Use the segment, not the tier label, when assigning playbooks.

**Alert threshold and accuracy.** The alert threshold is 0.5. From `part_c_final_test.csv`, of every 10 parcels flagged, about 6.9 are really delayed (precision 0.6889), and of every 10 delayed parcels about 7.6 are caught before they are late (recall 0.7561). That is the precision/recall trade-off the operations rule chose - it accepts some unnecessary calls to keep recall high.

**New parcels.** Of the 48 parcels about to be dispatched, 8 were flagged for action (`new_shipment_actions.csv`); 6 of those sit in Escalate hubs and are routed to "Escalate to hub manager", and the remaining 2 get a "Proactive customer call".

**Why K = 3.** The across-to-within separation ratio rises from 2.8940 at K=2 to 5.3928 at K=3, then more slowly to 6.3047 at K=4 and 6.8866 at K=5 (`part_d_separation.csv`). But the K=4 split is 8-7-5-4 (a cluster of only 4 hubs) and K=5 is 8-7-4-3-2 (a cluster of only 2 hubs) - too small to carry their own playbook. K=3 gives 9-8-7, three workable segments, and operations runs exactly three playbooks, so K=3 is kept.

## Production plan

**(a) Production-readiness characteristics mapped to this repository.**
- *Accuracy* - validated end to end: regression test R2 0.9493 (`part_b_metrics.csv`) and classifier test F1 0.7209 (`part_c_final_test.csv`).
- *Reliability* - the reload check (`part_d_reload_check.csv`) shows the saved pickle reproduces the in-memory probabilities to within 0.0, and `predict_delay.py` is byte-identical across runs.
- *Reproducibility* - `requirements.txt` pins exact versions, `generate_data.py` uses fixed seeds, and every model step uses `random_state=42`.
- *Performance (speed)* - a random forest of 100 trees on 840 rows fits in seconds; scoring 48 new parcels is instant.
- *Maintainability* - cleaning and feature logic live once in `src/shipment_prep.py` and are imported everywhere, so a fix is made in one place.
- *Consistency (same preprocessing in training and prediction)* - `predict_delay.py` imports and calls the same `clean_shipments` and `build_features` used in Part A, with the stored medians, so a new parcel is featurised exactly like a training parcel.
- *Monitorability* - every output is a versioned CSV, so drift and quality can be checked from files alone.

**(b) Quantities to monitor, with numeric triggers.**
- *Weekly delayed share of delivered parcels* - trigger an investigation if it moves above 0.25 (the training level was 0.2317).
- *Weekly share of parcels flagged for action* - trigger a review if it falls outside 0.10-0.40 (8 of 48 = 0.1667 on the new batch).
- *Recall measured on parcels whose outcome is now known* - trigger a retrain if recall drops below 0.70 (test recall was 0.7561).

**(c) Retraining schedule and the sale window.** Retrain monthly, or immediately when any monitor above breaches its trigger. The 15-28 September sale window (`sale_event_flag=1`) materially changes delay behaviour (it adds hours to Express parcels in particular), so performance during a sale must be compared against another sale, not against ordinary weeks; keep the flag in the data and segment evaluation reports by sale/ordinary weeks. Data drift would show up here as the distance distribution shifting toward longer lanes, the hub-level delay rate rising in a previously Standard hub, or the weekly delayed share breaching 0.25 - any of these means the model is going stale.

## Limitations

- The data is synthetic and generated from a known linear rule, so the strong fits (regression R2 0.9493, classifier F1 0.7209) are cleaner than real logistics data, where unmeasured factors (traffic, rider availability, weather beyond the rain flag) would lower accuracy.
- The test set has only 41 delayed parcels, so test precision (0.6889) and recall (0.7561) have wide uncertainty; a single extra false negative moves recall by about 0.024.
- The alert threshold (0.5) was tuned on one validation split of 180 rows, so it is calibrated to that specific split and could be fragile if the live delay mix shifts.
- The classifier is a single random forest with no calibration; `predict_proba` is a vote fraction, not a calibrated probability, so the 0.5 threshold is a decision boundary rather than a true probability statement.
